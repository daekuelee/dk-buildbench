# research tech — 기능에 맞는 기술 선택의 근거를 구한다

1. 필요한 기능과 이번에 정할 것을 밝힌다. plan의 제약·현재 스택과 context의 확인된 환경을 읽는다.
2. `../references/sources.md`에 따라 필요한 출처를 고른다. 버전·지원 여부·정확한 사용법에 웹 확인이 필요하면 범위를 제안하고 허락을 받는다. 기존 스택으로 가능한지 먼저 본다. 실제 선택이 남아 있을 때 후보를 비교한다. 이미 결정한 것을 형식상 다시 비교하지 않는다.
3. 언어·실행 환경, 화면 구성, 기능별 라이브러리·공개 레포를 역할별로 구분한다. toolkit/reuse.md에 따라 전체 사용·부분 활용·설계 참고·직접 구현을 필요한 범위에서 비교한다. 탐색이 넓으면 요구 중 구현·오류 비용이 큰 기능으로 좁힌다. 생략했다면 그 이유와 미확인을 남기며 조사하지 않고 후보가 없다고 단정하지 않는다.
4. 요구·환경에 맞는 후보의 역할·차이·사용 조건·찾기·이해·연결·검증·수정 비용을 설명한다. PROFILE은 학습·설명 비용에 사용하며 낯선 기술을 자동 제외하지 않는다. 준비한 후보도 현재 요구의 작은 입력·기대값으로 다시 확인할 필요를 판단한다.
5. 추천과 근거, 감수하는 한계, 아직 확인하지 못한 것을 밝힌다. 중요한 선택의 이해는 toolkit/understanding.md를 따르고 사용자 이유의 원문을 decisions에 한 번 연결한다. 사용법이 판단에 필요하면 공식 문서의 작은 예를 출처와 함께 보인다.

## 비교가 결론을 떠받치는지 확인한다

- 현재 선택을 바꿀 불확실성 하나와 그것을 가를 작은 확인부터 고른다. 남은 시간·자원에 맞춰 확인 범위와 멈출 조건을 밝힌다. 모든 후보의 설치·전수 벤치마크를 의무화하지 않는다.
- 후보의 기본 설정 실패, 환경 제약, 기능 자체의 부재를 구분한다. 후보마다 필요한 기능·보안·연결 범위를 맞춰 비교하고, 직접 만들 부분의 비용도 센다. 한 번의 실행 시간과 익숙함만으로 일반 우열을 선언하지 않는다.
- 추천을 뒤집을 조건이나 반례가 무엇인지 밝힌다. 다른 환경의 실측은 그 환경의 증거이며 현재 환경에서는 필요한 부분만 다시 확인한다. 가정으로 만든 개선 수치를 업무 성과로 부르지 않는다.

설치하지 않는다. 설치는 사용자가 선택하고 plan에 기록한 뒤 메인 세션이 한다. 새 프레임워크의 학습 비용과 설명하기 어려워지는 부분도 판단 재료다. 기록은 SKILL의 실행 주체별 규칙을 따른다.
