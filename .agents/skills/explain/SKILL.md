# explain — 이해하고 판단할 수 있게 설명한다

사용자의 질문과 이미 있는 근거에서 시작한다. PROFILE.md의 이해도에 맞춰, 질문에 답하거나 선택의 차이가 드러나게 쓴다. 보고 형식을 채우려고 새 조사나 결정거리를 만들지 않는다.

## op
| op | 입력 | 읽을 절차 |
|---|---|---|
| understand | 질문과 설명할 코드·개념·동작 | [ops/understand.md](ops/understand.md) |
| decide | 지금 정할 일과 근거·선택지 | [ops/decide.md](ops/decide.md) |
| prep | 실제 구현·결정·변경·검증 기록 | [ops/prep.md](ops/prep.md) |

해당 op 파일을 읽고 수행한다. 과제의 자료·환경 정보가 필요하면 docs/context.md를 읽는다. 짧은 질문에 전체 보고 양식을 적용하지 않는다.

## 표현과 출력
- 설명 깊이는 [references/depth.md](references/depth.md)에 따라 질문의 목적과 막힌 연결로 고른다. 얕은 답을 기본 성공으로 삼지 않으며, 이미 아는 내용과 현재 선택에 불필요한 내부 원리는 생략한다.
- 결론이나 직접 답을 먼저 쓴다. 실제로 정할 것이 있으면 선택할 내용과 추천 근거를 바로 보여 준다.
- 한 문장에 사실 하나를 담고 동사를 쓴다. 새 낱말은 쓰기 전에 풀어 준다. PROFILE에서 익숙한 영역은 기초 설명을 생략한다.
- 관계를 이해하는 데 도움이 되면 그림, 비교에는 표, 동작에는 실제 값으로 따라가기를 쓴다. 모든 답에 세 가지를 다 넣지 않는다.
- 중요한 동작·선택 설명은 사용자 행동 하나와 값 하나를 고정해 시작한다. 그림의 번호·대상·값을 본문에서도 유지하고, 입력이 어떻게 변하는지와 그 장치가 없을 때의 실패를 연결한다. 추상적인 평가 용어를 먼저 나열하지 않는다. 확인된 사례가 없으면 가상 예시임을 밝히며 사용자 요구·선택으로 기록하지 않는다.
- 상세 보고는 docs/reports에 쓴다. 제한된 에디터 환경에서는 Markdown과 고정폭 그림으로 흐름·분기·경계를 보여 준다. 사용자가 시각적인 페이지를 요청하고 볼 수 있는 환경이면 실제 SVG 등 구조 도식과 본문을 연결한 HTML로 만든다. 텍스트 대체본이 필요하다는 이유로 시각 보고서까지 텍스트 도식으로 통일하지 않는다. [references/text-visuals.md](references/text-visuals.md)의 기준을 필요한 만큼 쓰고 핵심 설명은 MD에서도 유지한다. 그림을 먼저 두고 읽기 안내를 붙이며 중요한 인과 설명을 접힌 영역에 숨기지 않는다. 외부 게시 없이 채팅에 결론과 링크를 남긴다. 선택의 차이·추천 이유는 채팅에도 보인다.
- 읽지 않은 대상과 확인 못 한 동작을 아는 것처럼 쓰지 않는다. 필요한 새 조사는 부족한 근거로 표시하고 사용자와 범위를 정한다. 질문한 동작을 한 번 실행하는 국소 확인은 할 수 있다.
- 메인 세션은 완료한 op를 state에 한 줄 기록한다. 읽기 전용 역할은 형식을 참고해 답만 반환하고 파일을 쓰지 않는다.
- 사용자의 판단·이유·답안은 대신 쓰지 않는다. 칭찬·다짐·형식적인 끝의 복습 질문은 붙이지 않는다. 중요한 선택·결과 수용에는 작업 루트의 toolkit/understanding.md를 적용해 작은 예측·선택·해석으로 이해를 확인한다. 이미 확인됐다면 반복하지 않는다. 분야 개념이 막히면 toolkit/index.md에서 관련 카드만 읽는다.
