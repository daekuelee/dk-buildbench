# 라이브러리·공개 레포를 준비해서 가져갈 수 있을까?

가능한 준비 방식이다. 단, 이 문서는 특정 후보를 조사·권장·검증한 결과가 아니라 **후보를 준비하고 선택하는 틀**이다. 실제 사용할 환경·자료 반입·외부 코드 사용 조건은 해당 과제의 안내에서 확인한다. 일반적인 허용·금지를 새로 만들지 않는다.

## 재사용의 네 수준

| 방식 | 무엇을 가져오나 | 확인할 핵심 |
|---|---|---|
| 설계 참고 | 구조·접근법을 이해해 현재 요구에 맞춰 설계 | 같은 문제가 맞는지, 예제의 가정이 현재에도 성립하는지 |
| 기능 일부 활용 | 독립적인 함수·모듈·예제 코드 | 연결된 의존성, 사용 조건, 입력·출력·예외, 현재 요구의 기대값 |
| 라이브러리 사용 | 공개 인터페이스로 기능 호출 | 지원 기능·환경, 연결·이해 비용, 실패 처리, 요구에 대한 검증 |
| 프로젝트 전체 기반 | 앱·프레임워크 구성을 출발점으로 사용 | 불필요한 기능·설정, 데이터 모델·흐름의 적합성, 전체 실행·수정·검증 비용 |

라이브러리도 공개 레포를 통해 개발될 수 있다. 위 구분은 저장 장소가 아니라 **얼마나 가져오고 어떤 책임을 맡기는지**에 관한 것이다. 유명함·별 수·데모 실행만으로 현재 요구에 적합하다고 판정하지 않는다.

## 준비 때와 풀이 때를 구분

준비 때는 자주 필요한 기능군의 후보를 좁혀 실제로 실행해 보고 최소 예제·입출력·한계를 기록할 수 있다. 이 작업은 낯선 프로젝트를 풀이 도중 처음 이해하는 비용을 줄일 가능성이 있다. 그래도 현재 과제 적합성을 다시 확인해야 한다.

풀이 때는 요구·환경 → 이미 준비한 후보 또는 기존 코드 → 적합성 확인 → 작은 동작·독립 기대값 검증 → 채택 또는 직접 구현 순서로 판단한다. 준비 목록이 특정 기술을 강제로 고르게 만들면 안 된다.

프로젝트 전체의 넓은 탐색이 길어질 것 같으면, 직접 만들 때 가장 어렵거나 오류 비용이 큰 기능으로 범위를 좁힌다. 탐색을 생략했다면 그 이유와 확인하지 않은 것을 남긴다. 찾아보지 않고 ‘적합한 것이 없다’고 쓰지 않는다.

## 후보 하나의 기록 틀

- 기능과 적용 조건: 어떤 일을 맡기며 언제 유리한가.
- 원본·확인 시점·버전 또는 커밋: 어디의 무엇을 확인했는가.
- 사용 조건과 환경: 재사용에 필요한 조건, 의존성, 실행에 필요한 자원.
- 최소 실행 사례: 입력·실행 방법·관찰한 출력. 아직 실행하지 않았으면 미실행 표시.
- 독립 기대값과 출처: 실행된다는 것과 맞는다는 것을 구분.
- 이해해야 할 경계: 맡긴 기능, 직접 작성할 업무 규칙, 중요한 실패·제약.
- 도입 비용과 대안: 찾기·이해·연결·검증·수정 비용, 직접 구현·기존 도구와의 차이.
- 채택 범위·미확인: 전체·일부·참고 중 무엇인지, 어떤 조건이면 사용을 포기할지.

## 현재 후보 상태

등록된 검증 후보 없음. 현재는 외부 검색·다운로드·설치·코드 재사용을 하지 않았다. 유명 레포 이름만 채운 목록을 준비 완료로 취급하지 않는다. 실제 후보 선정은 필요한 기능군·준비 시간·환경을 정한 별도 작업이며, 일반화된 기능 수준으로 준비한다.
