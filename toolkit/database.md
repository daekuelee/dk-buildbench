# DB·상태: 무엇이 남고 언제 바뀌나

언제: 여러 요청·사용자·재실행 사이에 정보를 보존하거나 연결해야 할 때. 일회성 계산에 DB를 의무화하지 않는다.

## 최소 지도

현실의 한 대상 → 한 건의 기록 → 구분하는 키 → 관련 기록 → 변경 조건 → 저장 결과.

키는 기록을 구분하는 값이다. 여러 변경이 전부 성공하거나 전부 취소되어야 하는 묶음이 필요한지는 업무의 일관성 조건에서 판단한다.

## 사람이 판단할 것

- 한 건이 무엇인지, 같은 이름·다른 건을 어떻게 구분하는지.
- 무엇이 원본이며 무엇이 계산해서 얻는 값인지.
- 중복 요청·삭제·부분 실패·동시 변경이 중요한지. 관련 없는 경우까지 모두 구현하지 않는다.
- 재실행 후 무엇이 남아야 하며, 파일·기존 저장소·새 DB 중 어떤 방식이 요구와 비용에 맞는지.

## 작은 적용

이름이 같은 대상 둘을 다른 기록으로 다뤄야 하는 가상 요구를 놓고, 이름을 키로 쓰면 생기는 결과를 확인한다. 같은 요청을 두 번 받았을 때 한 건·두 건 중 무엇이 맞는지는 실제 업무 기준으로 정한다.

## 확인과 멈출 곳

작은 표본의 저장 전·후 상태를 앱 밖에서 예상하고 실제 결과와 대조한다. 필요한 경우 재실행·중복·부분 실패를 확인한다. 저장 성공 메시지만으로 기록의 정확성을 판정하지 않는다. 내부 저장 엔진의 모든 원리보다 기록·관계·변경의 보장을 이해한다.
