# 백엔드: 요청에서 결과까지

언제: 사용자 요청을 받아 업무 규칙·외부 호출·저장을 처리하는 부분이 있을 때. 파일 변환만 하는 작업에는 서버가 필요하지 않을 수 있다.

## 최소 지도

사용자 동작 → 요청의 값 → 입력·권한 확인 → 업무 처리 → 필요한 저장·외부 호출 → 응답 → 화면의 결과.

프레임워크는 이 흐름에서 요청을 연결하거나 실행을 관리하는 도구다. 무엇을 도구가 맡고 어떤 업무 규칙을 우리가 작성하는지 구분한다. 제품 이름이나 내부 구조보다 실제 요청 한 건으로 설명한다.

## 사람이 판단할 것

- 입력·출력·실패 처리의 의미와 현재 성공 조건.
- 어디서 어떤 상태가 바뀌는지, 외부 호출이 실패하면 어떤 결과를 보여 줄지.
- 기술 선택이 남았다면 기존 환경, 요구 충족, 연결·학습·검증 비용과 대안의 차이.

## 작은 적용

가상의 ‘작업 요청 확정’ 기능이라면 확정 가능한 조건과 실패 시 상태를 먼저 정한다. 요청 값이 잘못됐는데 저장부터 일어나면 어떤 문제가 생기는지 따라간다. 실제 업무의 확정 조건은 예시에서 가져오지 않는다.

## 확인과 멈출 곳

예상 응답과 저장 결과를 요구에서 정하고 실제 입력으로 대조한다. 서버 기동은 업무 동작의 증거가 아니다. 핵심 경로·선택 영향·실패 확인 지점을 이해하면 다음 작업으로 넘어가며, 프레임워크 내부 호출 전체를 암기하지 않는다.
